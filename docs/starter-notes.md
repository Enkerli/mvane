# FM-1 harmony instrument starter

This package gives the local developer a portable C99 harmony module, a console demo, and the integration plan below. The module is a newly written prototype. Replace or extend its phrase rules with the actual ProgGenie module once you have the local source. The archive contains no hardware firmware image, third-party factory presets, or Vane DSP.

## Start here

Unzip, enter `fm1-starter`, and run `make check`. Ubuntu Studio needs a native C compiler and make (Ubuntu's `build-essential`). On the MacBook Air, Apple Command Line Tools (`xcode-select --install` if needed) are enough for this step. The demo prints bass and voicing MIDI notes for a C major ii–V–I. Checks cover three phrase templates in all 12 keys, live and loop voicing, and selected invalid inputs.

`harmony.c` and `harmony.h` have no UI or SDK dependencies. `harmony_phrase` writes up to four chords into a caller-provided array (capacity at least four). `harmony_voice_live` selects against the currently sounding upper voices. `harmony_voice_loop` scores an entire phrase of up to eight chord events, including the last-to-first transition. It uses caller-owned scratch, 872 bytes on the tested host, plus small stack arrays. It searches compact voicings and scores register and movement. The prototype uses 12-TET MIDI pitches, a fixed bass octave, and deterministic templates. Future ProgGenie integration can add substitutions, locked chord slots, duration-aware phrasing, and voicing families using the same event boundary.

## Build and verify the platform

1. On the Ubuntu Studio miniPC, use the x86-64 native JieLi toolchain. Clone [fm1-base](https://github.com/charlesvestal/fm1-base) with submodules. Pin the base revision once the template works and record the BSP revision, toolchain and hardware version. Follow the pinned checkout's README for `tools/setup_toolchain.sh`, the AC79 SDK packaging files, Python/Pillow and the template build. On the M1 MacBook Air, native builds cover desktop tests and the simulator. Use the upstream Docker or Podman route for the Linux x86-64 hardware compiler, or build the device package on Ubuntu and transfer it as a file.
2. Build the upstream template unchanged in the simulator and for the device. Check the exact storage chip and supported updater for your FM-1. Export full backups from installed firmware, and confirm you have the correct stock package and recovery workflow before loading a dev image. Store your own new app sources and pinned platform revisions with the handoff. [Build prerequisites](https://sbegueria.github.io/fm1-dev-wiki/Getting-Started.html) · [Recovery](https://sbegueria.github.io/fm1-dev-wiki/Recovery.html)
3. Verify USB duplex with the template or an audible minimal app. Enable both `usb_audio_in` and `usb_audio_out` in the app configuration. With the iPad as USB host, record the synth into AUM or Logic while playing a backing track to the FM-1 headphones. The synth capture should exclude the backing track. Repeat on Ubuntu and macOS as available. Record supported rates, dropout counts and disconnect/reconnect behaviour with MIDI active. Begin with USB MIDI and TRS MIDI. When the iPad or computer is the USB host, route Exquis and AirMotion Neo through that host or via a suitable TRS MIDI source. Test the actual routing with your setup.
4. Add the harmony module to the template build using its app manifest. Map note generation to the platform's existing MIDI, key and control callbacks. Prepare phrase/voicing changes on the control side and deliver bounded note events to the renderer. Start with a cheap polyphonic VA or FM engine, four upper voices, bass and one reserved lead voice. Give bass, chord and lead separate event ownership, including same-pitch events. At phrase transitions allow common-tone hold, release voices that leave, and start new voices. Release owned voices on stop or disconnect. Establish internal playback first, then add optional MIDI out and external clock once the note lifecycle is stable.
5. Bring up expression on the lead. For Exquis use lower-zone member-channel bend, pressure and CC74, with range agreement and controller state reset on reallocation. Verify two independent notes in an expression test patch even if the first combined performance reserves one lead voice. For AirMotion Neo use CC2 for smoothed gain plus brightness, with a playable breath curve and a legato patch. Scope breath to the target part and allow it to arrive on a different channel or port from the notes. Confirm that bending one Exquis note cannot bend the backing and that zero breath does not mute the backing in lead mode. Exercise sustain, overlapping releases, repeated notes and panic with duplex streaming active.

## Session recording and retroactive capture

Treat a session as a performance-event recording. Capture the played notes, chord and phrase choices, MPE member-channel pitch bend, pressure, CC74, breath CC2, sustain, sound changes, tempo and transport. Keep generated backing events identifiable from the player's events so the session can be reopened as an editable performance, exported as MIDI where MIDI can represent it, or replayed internally without duplicating generated notes.

Run the event recorder continuously whenever the instrument is playable. Use a fixed-size RAM ring buffer and compact, timestamped events. Do not allocate memory or write flash in the audio callback. A useful first target is the preceding 30 seconds or 8 bars, selectable as **Last phrase** and **Last 30 s**. Pressing REC after playing copies the chosen interval into a session take, reconstructs notes and controllers already active at the capture boundary, and continues recording until REC or STOP. Pressing REC before playing starts an ordinary take. A second press commits it. HOLD + REC can provide **Capture last phrase** if a dedicated gesture is needed, but expose the action and available duration on screen rather than relying on an undocumented shortcut.

Record time in two domains. With internal or external clock, store musical ticks plus microtiming so tempo can change on replay. Without a clock, store elapsed sample-frame or microsecond time and derive an editable tempo only if the user asks. On capture, include the most recent value of every active expression controller at time zero, synthesize note starts for notes held across the boundary, and preserve their later releases. Track notes by input port, MIDI channel and note so MPE, overlapping pitches and separate breath-plus-grid inputs survive the round trip. Panic, disconnect and mode changes must close or cancel active events deterministically.

Keep the current take in RAM during performance. Save it to flash only after STOP or an explicit Save action, because erasing the FM-1's NOR flash interrupts execution and can cause an audible gap. Use a versioned session file with length, clock mode, tempo map, event count and CRC, committed through A/B storage or the platform's transactional file service. If the take is larger than the available device slot, send it to the companion editor before replacing it. The editor should offer **Save session**, **Open session**, **Export MIDI**, and **Render/record audio**. A standard MIDI file can carry notes, CC2, CC74, channel pressure and pitch bend. Keep a native session file as the authoritative form for generator commands, preset references and any timing or expression data that MIDI export simplifies.

Full-quality retroactive **audio** is a separate feature. The stock device has no external RAM and only 1 MiB of shared flash, so an onboard rolling stereo-audio history would consume the available memory very quickly and compete with WindCore delay lines, voices and USB buffers. For the first milestone, stream class-compliant USB audio continuously and let AUM, Logic, Bitwig or a small companion recorder keep the rolling audio buffer. The FM-1 can send a marker when a retrospective take is captured so the host extracts the matching audio interval. If a later device test finds enough headroom, evaluate a very short compressed mono scratch buffer as a convenience, without making it the master recording.

## Front panel and presets

Use a single performance screen. Show the current mode, sound, key and chord or phrase, with on-screen labels for the available knob actions. A workable starting layout is **Sound**, **Key**, and **Voicing** in Chord mode, and **Sound**, **Key**, and **Variation** in Phrase mode. Show the current and next chord during playback. Keep play/stop and mode selection visible. Put expression setup on a short page with **Grid MPE** and **Breath + keys** profiles and a live indicator of incoming expression. Keep drums, multitrack recording and song arrangement out of the milestone. Match control labels to legible physical controls after using the template on hardware.

Start from two or three favourite donor sounds. Record the firmware version, preset name, engine, oscillator/operator settings, envelopes, filter and any dependencies. Render a short reference with fixed MIDI notes and velocities. Port the corresponding engine and parameter mapping where practical, or recreate the sound on a shared engine and compare by ear. Make expression part of the patch design. A soft pad can use per-note CC74 to open the filter. An FM keys patch can map pressure to modulation index. A breath lead should respond at low breath and swell smoothly. Include one dry expression demonstration with each factory patch.

### Getting sounds out of your current firmware

- **Clipper.** Open the [Clipper Editor](https://isod89.github.io/clipper-fm1/webapp/editor/) in Chrome or Edge on a desktop and connect the FM-1. In Library, use **Save current sound** or copy a device or factory preset into the library. Select a library entry and use **Export** for an individual file. To transfer one back, use **Import → Audition → To device slot**. In the Sound tab, HYBRID has its own Import/Export patch workflow (`.clipper.json`), and FMX and FM6 have engine-specific formats. Collect both a complete Library sound and any referenced bank/table assets where applicable. [Clipper quick start](https://github.com/isod89/clipper-fm1/blob/main/QUICKSTART.md)
- **CoralFlower.** Preserve a backup through the [CoralFlower installer](https://ficusficusov.github.io/CoralFlower/), record the exact firmware version and preset names, and collect settings from the sound editor. The documented backup includes sounds along with other device state. An individual-sound reimport workflow remains unverified. Use an exported backup from the actual firmware version to identify the structures before implementing a converter. [CoralFlower source](https://github.com/FicusFicusov/CoralFlower)

### Transfer workflow for this firmware

Make **Open preset → Audition → Save to slot** the primary path in the desktop editor. Show the sound name, required engine, expression mappings and selected device slot. Audition changes only the active sound in RAM. Save is explicit, and the editor reads the slot back to confirm success. Keep **Export preset** next to it and place device-wide backup and restore on a separate page.

Define a versioned single-preset JSON interchange with engine ID and revision, stable parameter IDs, expression routes and referenced assets. Validate the format, bounds and engine compatibility on import. Start with one round-trip preset and a bounded, versioned USB transfer via the platform's app command path. Stage the transfer, validate before applying it, and verify that interruption or a bad file leaves the previous saved sound playable. The device can store a compact validated representation; JSON can remain on the desktop. Add donor converters only after you have representative exported files and a mapping to a supported engine. Preserve file-level notices for reused code and assets.

## Vane DSP feasibility

Plan for a mono WindCore lead first. From the local Vane checkout, trace one patch from initialization and note events to its render loop. Inventory dependencies, per-voice delay buffers, tables, math functions, oversampling and any upstream code or assets. Keep host/plugin wrappers out of the device target. Extract the reusable DSP and build a desktop reference render at the FM-1 app's sample rate. Include soft and hard attacks, long notes, a legato scale, lowest intended pitch and abrupt breath changes. Use the same input events when testing Frankensax locally.

Use the device link map to account for flash, static RAM, stack, USB buffers and delay lines. For each modeled delay start with its required sample count at the lowest supported pitch, including interpolation margin. Measure one WindCore voice alone and then with four chord notes, bass and USB duplex. Log worst render-block time, missed deadlines and USB underruns with effects off, then with the proposed effects on. Use actual block size / sample rate as the deadline, and choose headroom from the measured workload. Prefer float32 in the hot path and check code generation for accidental double precision. Optimize only after profiling. If one voice exceeds the budget, test reduced oversampling, an engine-specific lower rate with appropriate filtering, or a simpler resonator. Measure Frankensax independently. [Hardware overview](https://sbegueria.github.io/fm1-dev-wiki/Hardware-Overview.html) · [Performance](https://sbegueria.github.io/fm1-dev-wiki/Performance.html)

## First acceptance run

From power-on, choose the sound and play a chord with the front-panel labels alone. Start a ii–V–I, play the expressive lead through a complete loop, then press Capture last phrase after the fact. Replay the take and compare notes, held-note boundaries, breath, per-note expression and timing. Continue recording for another phrase, stop, save, restart and reopen it. Monitor a host backing track and record the synth audio while hosting USB MIDI. Stop and confirm silence after release tails. Export one preset, audition it, save it to another slot, restart and load the saved copy. Record the firmware commit, board and flash info, host and sample rate, event-buffer capacity, longest retained interval, peak render time and any USB underruns in the handoff. The archive's desktop check covers the harmony core. This acceptance run requires the device integration and hardware.
